# 任务记录：自动保留与手动清理

## 为什么需要

真实机器上的 `.iexa-jobs.json` 已经是 **500 条 / 263.8 KB**，而且全部来自同一个会话、
同一天。原因是旧逻辑只有一句 `jobs.slice(-500)`：全局计数上限，不看时间，也不分会话。

这带来两个问题：

- **列表**：折叠后一条 33px，500 条仍是 16,500px 的滚动区，每次轮询都要走一遍。
- **存储**：`JsonStore.save` 每次把整个数组序列化，一个回合几十次 job 事件就要写几十遍。

## 自动保留

```
7 天      —— 已结束的记录超过 7 天丢弃
200 条    —— 每个会话最多保留 200 条已结束记录（保留最新的）
500 条    —— 全局上限，作为最后一道保险
```

**运行中的记录永不丢弃**：`queued` / `awaiting_approval` / `running` / `cancelling`
四种状态不受时间和数量限制，否则任务中心会丢掉正在进行的进度。

裁剪在 `pruneJobs()` 里做，从数组**末尾向前**遍历（数组是追加顺序，末尾最新），
所以触发上限时丢掉的总是最旧的那条。两个时机：

1. `loadJobs()` 首次读取——顺手把裁剪结果写回磁盘，启动即瘦身，不必等下一次任务事件。
2. 每次 `saveJobs()`——上限始终生效，文件不会再长回去。

## 手动清理

头部的 `清理` 按钮，范围**跟随当前筛选项**：

| 筛选 | 清理范围 | 确认文案 |
|---|---|---|
| 当前会话 | 只清这个会话 | 清理当前会话中已结束的任务记录？正在运行的任务会保留 |
| 全部会话 | 清所有会话 | 清理全部会话中已结束的任务记录？正在运行的任务会保留 |

清完立刻 `loadJobs()` 重新拉取，列表、徽标、空状态一起更新；写入走 `saveSync`，
跳过 150ms 的防抖，避免刚点完就退出导致清理丢失。

服务端接口：

```
GET    /api/jobs[?sessionId=]   -> { jobs, retention: { days, perSession, total } }
DELETE /api/jobs[?sessionId=]   -> { ok, removed, remaining }
```

`retention` 随数据一起返回，面板直接用它拼那句「自动保留 7 天、每个会话最多 200 条」，
避免界面文案和服务端常量各说一套。

## 权限

`/api/jobs` 的 `DELETE` 和 `/api/token-usage` 一样，只允许桌面端：配对手机（`chat`
能力）可以读审计记录，不能清。判定在 `routeAllowedForDevice()`。

## 顺带

- `jobsExpanded` 里的 id 会随卡片删除一起清掉，不再是只增不减的 Set。
- 头部两个按钮包进 `.jobs-actions`，各自保持 60px 固有宽度（之前 flex 会把它们拉满）。

## 验证

`tests/jobs-retention.test.js`（653 条夹具：会话 A 400 条已结束 + 2 条运行中，会话 B 250 条
其中 40 条过期，会话 C 只有 1 条过期）：

| 断言 | 结果 |
|---|---|
| 首次读取后记录数 | 402（A 200 + 2 运行中，B 200，C 0） |
| 过期记录 | 全部消失 |
| 运行中记录 | 2 条全留 |
| 磁盘文件 | 同步缩到 402 条 |
| `DELETE ?sessionId=sess_a` | removed 200 / remaining 202，B 不受影响 |
| 再删一次 | removed 0（幂等） |
| 全局 `DELETE` | removed 200 / remaining 2，只剩运行中 |

`tests/browser-jobs-clear.test.js`（真实 Chromium，8 条种子数据）：确认框文案跟随筛选、
取消不动数据、确定后列表只剩运行中那条、徽标变 1、磁盘文件同步为 1 条。

全量 **665 / 665**。

## 对现有安装的影响

下次启动时，第一次读取任务记录就会按新策略裁剪并写回。以当前这份 500 条的数据为例：
全部是今天的记录，按会话上限保留最新 200 条，文件约从 264 KB 降到 105 KB。
想立刻清空则点 `清理`。
